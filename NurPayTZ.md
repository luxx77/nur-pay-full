# Nur Pay — спецификация бэкенда (прототип)

## Контекст

Nur Pay — closed-loop электронный кошелёк для Туркменистана. Ориентир — Touch 'n Go (Малайзия). Это НЕ полноценная платёжная система: деньги двигаются только внутри платформы (между пользователями и мерчантами).

- Текущая цель: прототип для презентации. Надёжность и безопасность — на уровне "презентабельно и логически корректно", не продакшн.
- Фронтенд: Flutter. UI на туркменском (латиница). UI для юзера и мерчанта сделан раздельно.
- Долгосрочный план (к бэкенду прототипа отношения не имеет): запуск совместно с МВД Туркменистана на базе их приложения Galkan Töleg.

## Что НЕ входит в прототип

- KYC и уровни верификации
- Deep links, webhooks, API для IT/SaaS-оплат
- OTP / SMS-подтверждение
- JWT и любые токены сессий
- Возвраты (refunds)
- Кассиры-агенты для пополнения наличкой
- Вывод денег (cash-out), пополнение с карт
- Лимиты на счёт/операции (кроме max-суммы в QR оплаты, см. ниже)

## Деньги

- Все суммы хранятся и считаются в теңңе (1 манат = 100 теңңе) как целые числа (BIGINT). Никаких float/decimal.
- Во фронт можно отдавать в теңңе; перевод в манаты (деление на 100) — только при отображении.

## Комиссии

- В .env, в процентах (целые числа):
  ```
  ACTIVATION_FEE=1
  MERCHANT_PAYMENT_FEE=1
  ```
- P2P-переводы — без комиссии.
- Формула: `fee = floor(amount * fee_percent / 100)`. Округление всегда вниз.
  - Следствие: при оплате меньше 100 теңңе комиссия = 0 автоматически, без отдельных if-ов. 150 → 1, 250 → 2.
- Комиссию платит ПОЛУЧАТЕЛЬ: основная проводка всегда на полную сумму, комиссия — отдельная проводка от получателя на системный счёт fees.

## Пользователи

Одна таблица `users`, отдельной таблицы accounts/merchants нет.

- Поле `type`: `user` | `merchant` | `system`.
- Мерчант = пользователь с `type = merchant` (задаётся в БД вручную, хардкод-списков в коде нет).
- Системные пользователи (`type = system`), создаются сидом:
  - `issuance` — эмиссия; источник денег при активации кодов. Его баланс уходит в минус — это нормально, минус = сколько всего денег выпущено в систему (должно совпадать с наличкой, собранной мерчантами за активированные коды).
  - `fees` — сюда поступают все комиссии.
- У каждого юзера:
  - `public_qr_uuid` — UUID v4, статичный публичный QR для получения P2P-переводов. Отдаётся фронту.
  - `payment_secret` — случайный секрет, генерится ОДИН раз на юзера (не на сессию), хранится в БД, отдаётся фронту при авторизации. Используется для подписи QR-кода оплаты мерчанту.

## Авторизация (заглушка для прототипа)

- Юзер отправляет номер телефона → если юзера нет, создаём (генерим `public_qr_uuid` и `payment_secret`); если есть — сразу возвращаем данные, нужные фронту (включая `user_type`, `public_qr_uuid`, `payment_secret`). Без OTP.
- Во всех последующих запросах фронт шлёт в хедерах `user_id` и `user_type` (тип, которым он себя считает).
- Бэк сверяет `user_type` из хедера с `type` в БД. Если не совпадает — возвращает ошибку, по которой фронт делает logout.
- Осознанный компромисс: подменой хедера можно зайти за любого. На презентации позиционируется как заглушка под JWT.

## Ledger (источник правды для балансов)

Поля баланса нет. Баланс = сумма входящих − сумма исходящих проводок пользователя.

Модель проводки: перевод `from → to`.
- `id`
- `from_user_id`
- `to_user_id`
- `amount` (теңңе, BIGINT, > 0)
- `type`: `activation` | `p2p` | `merchant_payment` | `fee`
- `parent_id` — nullable; у проводки-комиссии ссылается на основную проводку; у основной = null
- `nonce` — nullable, UNIQUE; uuid v7 из QR-кода оплаты мерчанту (защита от повторного списания)
- `created_at`

Операция целиком достаётся запросом `WHERE id = X OR parent_id = X`.

Требование к целостности: любая операция со списанием (проверка баланса + запись проводок) выполняется в одной DB-транзакции с блокировкой строки пользователя-плательщика (`SELECT ... FOR UPDATE`), чтобы параллельные списания не увели баланс в минус. Исключение: `issuance` может уходить в минус.

## Коды активации (пополнение счёта)

Пополнение — только через коды активации, которые продаются за наличку через мерчантов.

Таблица `activation_codes`:
- `id`
- `code` (UNIQUE)
- `amount` (теңңе)
- `merchant_id` — через какого мерчанта продаётся код
- `status`: `active` | `used`
- `activated_by` — nullable, юзер-активатор
- `activated_at` — nullable
- `created_at`

Создание кода: админский эндпоинт, принимает `{ amount, merchant_id }`, возвращает код. При создании в ledger НИЧЕГО не пишется — код только обещание.

Активация (код на 100 манат = 10000 теңңе):
1. Атомарно: `UPDATE activation_codes SET status='used', activated_by=?, activated_at=now() WHERE code=? AND status='active'`. Если не обновилась ни одна строка — ошибка (код не существует или уже использован).
2. В той же транзакции пишем проводки:
   ```
   #1  issuance → user   10000  type: activation  parent: null
   #2  user     → fees     100  type: fee         parent: #1
   ```
   Юзер видит в истории +100 и комиссию −1.

## P2P-перевод

- Отправитель сканирует статичный QR получателя (`public_qr_uuid`, UUID v4), вводит сумму.
- Бэк проверяет баланс отправителя (с блокировкой) и пишет одну проводку:
  ```
  #1  sender → recipient  amount  type: p2p  parent: null
  ```
- Комиссии нет.

## Оплата мерчанту (мерчант сканирует QR юзера)

Генерация кода на фронте юзера:
- Юзер указывает на фронте максимальную сумму, которую можно списать по этому QR (`max_amount`).
- Фронт каждые 30 секунд генерирует новый QR с payload:
  - `user_id`
  - `max_amount`
  - `nonce` — uuid v7 (содержит время генерации)
  - `hash` — хеш `payment_secret` юзера по `max_amount + user_id + nonce` (рекомендуется HMAC-SHA256)

Обработка на бэке (мерчант отсканировал QR, ввёл сумму, отправил запрос):
1. Найти юзера по `user_id`, пересчитать хеш его `payment_secret` — должен совпасть.
2. Время из uuid v7 — не старше 30 секунд (без допуска на рассинхрон часов; осознанно, для прототипа).
3. `nonce` ещё не использован (UNIQUE на `ledger.nonce`).
4. `amount <= max_amount`.
5. Баланс юзера достаточен (с блокировкой).
6. Проводки (пример: оплата 100 манат):
   ```
   #1  user     → merchant  10000  type: merchant_payment  parent: null  nonce: <uuid v7>
   #2  merchant → fees        100  type: fee               parent: #1
   ```
   Юзер видит "оплатил 100", мерчант видит +100 и комиссию −1.

## Осознанные упрощения прототипа

- Auth через user_id в хедере вместо токенов.
- Нет OTP.
- Время QR проверяется по часам телефона без допуска: если часы сбиты, коды будут невалидны.
- Нет возвратов: при необходимости в будущем — отдельная обратная операция в ledger, старые проводки никогда не удаляются и не редактируются.
- При появлении сложных операций можно перейти с `parent_id` на общий `transaction_id`.

## Порядок работы

Таблицы проектируются по одной, после каждой — эндпоинты к ней. Порядок: `users` → `ledger` → `activation_codes`. Полную схему сразу не генерировать.
