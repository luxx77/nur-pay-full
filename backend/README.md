# Nur Pay — бэкенд (прототип)

Реализация по [NurPayTZ.md](../NurPayTZ.md). Go + Postgres, Gin, pgx/v5,
sqlc, goose. Прототип для презентации: авторизация — заглушка, токенов
нет.

## Запуск

```bash
cp .env.example .env
make db-up        # Postgres в docker (порт 5433: 5432 часто занят)
make migrate-up   # схема + сид системных счетов
make run
```

`make help` покажет остальное: `generate` (sqlc), `migrate-new name=…`,
`db-reset`.

## Деньги

Все суммы — целые в теңңе (1 манат = 100 теңңе), `BIGINT`. Ни одного
float в коде и схеме.

Поля баланса нет: баланс всегда считается по книге проводок. Проводки
только добавляются — `UPDATE` и `DELETE` по `ledger` не выполняются
нигде.

Комиссия: `floor(amount * percent / 100)`, платит получатель отдельной
проводкой на системный счёт `fees`. При сумме меньше 100 теңңе комиссия
обнуляется формулой, и проводка не создаётся вовсе.

Системных счёта два, с фиксированными id из сид-миграции:
`issuance` (эмиссия, уходит в минус — это объём выпущенных денег) и
`fees` (комиссии). Сумма всех балансов всегда ноль.

## Целостность

Каждая операция со списанием — одна транзакция:

```
SELECT ... FOR UPDATE по строке плательщика
  → чтение баланса
  → вставка проводок
```

Порядок важен: блокировка до чтения. Параллельное списание с того же
счёта встаёт на блокировке и после коммита первой транзакции видит уже
записанную проводку. Проверено: 30 одновременных переводов при балансе
на 15 — ровно 15 успешных, баланс сел в ноль и не ушёл в минус.

Блокируется тот, чей баланс проверяется. `issuance` не блокируется
никогда: баланс ему не проверяется, а блокировка выстроила бы все
активации в одну очередь. Мерчант при оплате тоже не блокируется — его
комиссия оплачена тем же платежом в той же транзакции.

Однократность обеспечивается базой, а не проверками в коде:

* код активации гасится самим `UPDATE ... WHERE status = 'active'`;
* повторная оплата по одному QR ловится уникальным индексом на
  `ledger.nonce`.

В обоих случаях проверено гонкой 10 параллельных запросов — проходит
ровно один.

## Авторизация

`POST /auth/login` по номеру телефона, без OTP: нет юзера — создаём,
есть — отдаём как есть. Возвращает `user_id`, `user_type`,
`public_qr_uuid`, `payment_secret`.

Дальше фронт шлёт заголовки `user_id` и `user_type`. Тип сверяется с
базой; несовпадение — `user_type_mismatch`, по нему фронт разлогинивает.

Админский эндпоинт защищён статическим ключом `ADMIN_API_KEY` в
заголовке `admin_api_key`.

Подменой заголовка можно зайти за любого — осознанное упрощение
прототипа, заглушка под JWT.

## Платёжный QR

Приложение юзера каждые 30 секунд собирает payload: `user_id`,
`max_amount`, `nonce` (uuid v7), `hash`. Подписывается HMAC-SHA256 на
`payment_secret` юзера по канонической строке:

```
<user_id>.<max_amount>.<nonce>
```

UUID в нижнем регистре, сумма — целое в теңңе, подпись в hex нижним
регистром. Время берётся из самого nonce; допуска на рассинхрон часов
нет — сбитые часы телефона сделают коды невалидными.

## API

Все пути, кроме `/healthz`, `/auth/login` и `/admin/*`, требуют
заголовков `user_id` и `user_type`.

| метод  | путь                          | что делает                              |
|--------|-------------------------------|-----------------------------------------|
| GET    | `/healthz`                    | живость сервиса и базы                  |
| POST   | `/auth/login`                 | вход по телефону                        |
| GET    | `/me`                         | данные текущего пользователя            |
| GET    | `/balance`                    | баланс по книге                         |
| POST   | `/transfers`                  | P2P по `public_qr_uuid`, без комиссии   |
| POST   | `/activation-codes/activate`  | пополнение кодом                        |
| POST   | `/merchant/payments`          | приём оплаты по QR (только мерчант)     |
| GET    | `/operations`                 | история, `limit` ≤ 200, `offset`        |
| GET    | `/operations/:id`             | операция целиком                        |
| POST   | `/admin/activation-codes`     | выпуск кода, ключ `admin_api_key`       |

В `/operations/:id` видны только те проводки, в которых участвует
спрашивающий: комиссию мерчанта плательщик не видит.

`direction` в проводке считается относительно спрашивающего: одна и та
же строка для плательщика `out`, для получателя `in`.

## Ошибки

Единый формат, машиночитаемый код — основной:

```json
{"code": "insufficient_funds", "message": "insufficient funds"}
```

| статус | когда                                                              |
|--------|--------------------------------------------------------------------|
| 400    | кривой ввод, `invalid_signature`                                   |
| 401    | нет или не проходит авторизация                                    |
| 403    | `user_type_mismatch` (разлогинить), `forbidden` (не та роль)       |
| 404    | объекта нет                                                        |
| 409    | бизнес-правило: `insufficient_funds`, `code_already_used`, `nonce_used`, `qr_expired`, `amount_exceeds_max` |

Несуществующий и уже погашенный код активации отвечают одинаково —
иначе по ответу можно перебирать чужие коды.
